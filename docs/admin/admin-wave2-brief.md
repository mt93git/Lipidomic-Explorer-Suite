# Admin, phase 1, wave 2: shared brief for agents

Read `docs/admin/admin-wave1-brief.md` first (what Admin is, decisions, visual language, data rules). This
file adds what changed and what wave 2 builds. Work on the ref you were given (`admin/phase1` tip).

## What changed since wave 1

- **Same database, same pipeline as Team.** Admin's schema `admin` lives in the same Supabase Postgres as
  Team's project library (`public.pilot_projects`, `pilot_members`, `pilot_files`, bucket `case-files`;
  see `pilot/supabase/schema.sql` and `permissions.sql`). A released dataset becomes a project in that
  library, so Team and Nexo open the same record. Admin never edits or deletes Team rows; it only inserts,
  and only through `admin.release_dataset`.
- **What goes into the library.** Team's loader merges every sheet of a workbook
  (`R/utils_data.R`, `load_one_file`), so the file written to `pilot_files` is the **analysis file**: only
  the `Abundance` and `Metadata` sheets. `Internal_Standards`, `QC_Injections` and `Provenance` go into a
  **companion file** kept by Admin (`admin.dataset`), never into `pilot_files`.
- **Release signers are configurable.** Two signatures by different people stay mandatory. Who may sign
  is a policy the lab Owner edits (default people: the lab's two scientific leads; never hard-code names
  or emails: seed nothing, the Owner sets it in the app).
- **Staging exists.** A real Supabase (GoTrue + PostgREST + Postgres) with Team's schema and the admin
  migrations runs on the lab server. `db/admin/test/staging.integration.mjs` proves sign-in, RLS, no
  delete and audit against it (10/10). Agents cannot reach it; the coordinator runs it. Extend that file
  with checks for what you add, in the same style.
- **Practice: TDD, integration, E2E, Pareto.** For each flow: unit tests for the logic (test first, see
  it red), one integration test at the real boundary (PGlite for SQL, the staging script for the full
  stack), and **one** Playwright E2E for the happy path. Not more. No test for trivial markup, no mocks of
  the thing under test, no speculative abstractions. Report every command you ran and its output.

## The contract between UI and database (wave 2)

All writes go through these `admin` functions (`SECURITY DEFINER`, `search_path` pinned, permission checks
inside, granted to `authenticated`). UI tasks code against these names and shapes; the DB task implements
them exactly. If a shape must change, say so in your report instead of silently diverging.

| Function | Who may call | Effect |
|---|---|---|
| `receive_shipment(p_order_id uuid, p_carrier text, p_tracking_number text, p_condition text, p_box_count int, p_notes text) returns uuid` | lab staff Operator+ | inserts `shipment` with `received_at = now()`, `received_by = auth.uid()`; order stage `request` → `received` |
| `register_samples(p_order_id uuid, p_shipment_id uuid, p_samples jsonb) returns setof admin.sample` | lab staff Operator+ | `p_samples` = array of `{full_name, client_sample_id, group1_term, group2_term, replicate_term, patient_term, time_point_term, matrix, volume_ul}`; all-or-nothing; codes assigned by the existing trigger; duplicate `full_name` rejected with a clear message; stage → `registered` |
| `accept_result_file(p_order_id uuid, p_storage_path text, p_sha256 text, p_sciex_os_version text, p_processing_method text, p_summary jsonb) returns uuid` | lab staff Operator+ | today batches are built by hand in SCIEX OS, so when the order has no batch it creates one marked as imported; inserts `result_file` as `accepted`; stage → `processed` |
| `set_release_policy(p_eligible_signers uuid[], p_required_signatures int) returns void` | lab Owner only | new table `admin.release_policy` (one current row, history kept, audited); `p_required_signatures >= 2`; empty list = any lab Owner or Admin may sign |
| `sign_dataset(p_dataset_id uuid, p_role text, p_note text) returns uuid` | an eligible signer | refuses a second signature by the same person and signers outside the policy |
| `release_dataset(p_dataset_id uuid, p_analysis_object_path text, p_analysis_sha256 text, p_analysis_size_bytes bigint, p_analysis_name text, p_companion_path text) returns uuid` | an eligible signer | refuses unless the policy's signature count is met by distinct people; freezes the dataset (`released`); creates one `pilot_projects` row (name: order code + title), `pilot_members` (client members as `viewer`, signers as `owner`) and one `pilot_files` row for the analysis file (its `object_path` must be `<project_id>/<sha256>`, Team's rule); stage → `released`; returns the project id |

Storage: the app server uploads the analysis file to bucket `case-files` at `<project_id>/<sha256>`
before calling `release_dataset` (so the project id is generated by the app and passed in the path, or
the function returns it first; pick the simplest and document it). Admin's own files (results TXT,
companion file) go to a private bucket `admin-files`, path `<client_id>/<order_code>/...`.

### Shared pieces both UI tasks create identically (so merges are trivial)

- `frontends/admin/playwright.config.ts`: `testDir: 'e2e'`, `use.baseURL: 'http://127.0.0.1:3110/admin'`,
  `webServer: { command: 'npm run dev -- --port 3110', url: 'http://127.0.0.1:3110/admin/sign-in',
  reuseExistingServer: true }`, one project `chromium`. Script `"e2e": "playwright test"`. Dev dependency
  `"@playwright/test": "1.55.0"`. E2E runs in demo mode (no Supabase env vars).
- Data seam: `src/lib/data/` holds one small module per area exporting async functions named after the
  contract above (`receiveShipment`, `registerSamples`, ...). Each has a demo implementation (in memory,
  per request cookie, like today's demo) and a live one that calls `supabase.schema('admin').rpc(...)`.
  The choice is the existing mock/live switch in `src/lib/environment.ts`. No repository framework, no DI
  container: a plain `if (live)`.

If Playwright browsers cannot be installed in your sandbox (no network), still write the spec, make sure
`npx playwright test --list` finds it, and say so; the coordinator runs it.
