Evidence: source inspection; two successful, targeted Node/PGlite probes applying this checkout's migrations and synthetic test seed; and an in-memory TypeScript probe executing this checkout's data modules with request/session/environment adapters substituted. Storage findings below concern the checked-in deployment, not an assertion about staging's current configuration.

1. **P1 — Direct signature inserts still bypass signer eligibility and duplicate-signature checks.** Locations: `db/admin/migrations/0004_policies.sql:133`, `db/admin/migrations/0004_policies.sql:149`, `db/admin/migrations/0005_wave2.sql:297` and `:307`.

   Under the default policy, an Operator receives `42501` from `sign_dataset`, but can insert their own signature directly into `admin.signature`, twice. The probe produced two active rows for one person. This bypasses the new signing rules and lets an excluded writer freeze a built dataset's content; finding 4 also turns such a signature into Team ownership on a subsequent legitimate release. **Minimal fix:** `REVOKE INSERT ON admin.signature FROM authenticated` and require `sign_dataset` for signing. Preserve retraction through a narrowly checked path; prevent direct unarchiving from resurrecting an ineligible or duplicate signature. A partial unique index on `(dataset_id, user_id) WHERE archived_at IS NULL` can enforce the duplicate rule across paths.

2. **P1 — A direct dataset update ignores the configured policy and skips Team creation.** Locations: `db/admin/migrations/0005_wave2.sql:129` and `:139`; surviving grant/policy at `db/admin/migrations/0004_policies.sql:128` and `:149`.

   With three signatures required and only Owner/Admin signatures present, an Operator can execute `UPDATE admin.dataset SET status = 'released' ...`. The probe returned `status = released, project_id = NULL`: the caller need not be an eligible releaser, only two people are counted, and neither the Team records nor the order-stage update is performed. **Minimal fix:** revoke the **table-level** `UPDATE` grant on `admin.dataset`, then grant an explicit whitelist of editable content/archive columns excluding release state and identifiers. Route withdrawal/superseding through a checked function if those operations must remain available. Revoking only `UPDATE(status)`, as suggested in `db/admin/README.md:101`, is insufficient: the probe still reported both table and status-column UPDATE privileges after that revoke. Keep release through the six-argument function.

3. **P1 — The one-argument release RPC remains an executable policy bypass.** Locations: `db/admin/migrations/0003_rules.sql:192`, `db/admin/migrations/0004_policies.sql:152`, `db/admin/migrations/0005_wave2.sql:317` and `:375`.

   Adding the six-argument function leaves `release_dataset(did uuid)` installed and granted to `authenticated`. A caller can still use the old RPC with `{ "did": "<dataset-id>" }`. With two of three required signatures, the probe successfully released through this overload and again obtained `project_id = NULL`. **Minimal fix:** drop `admin.release_dataset(uuid)` in the new migration. If compatibility requires retaining its name temporarily, revoke its execution from `authenticated` and `PUBLIC` and make it fail explicitly. It cannot perform the new release without the analysis-file arguments.

4. **P1 — A removed signer receives fresh Team ownership through their historical signature.** Location: `db/admin/migrations/0005_wave2.sql:358`; compare the eligibility filter at `:340`.

   The release threshold counts currently eligible signers, but the Team membership INSERT promotes every unarchived signature's user to `owner`. Reproduction: let an Operator sign while eligible; remove them from the policy and archive their `lab_staff` row; obtain the two remaining eligible signatures and release. The probe showed that the removed Operator received `pilot_members.role = owner` and could read the project through Team's RLS. This remains possible after closing direct signature INSERT. **Minimal fix:** apply the same current eligibility filter to the signer branch of the membership INSERT. Preserve historical signatures as audit evidence; an independently valid client membership can still produce the normal viewer role.

5. **P1 — The published analysis is not bound to the artifact the two people signed.** Locations: `db/admin/migrations/0005_wave2.sql:338`, `:346` and `:363`.

   After collecting signatures on a frozen dataset, a single eligible release caller supplies an arbitrary analysis path, digest, size and companion path. Validation relates the supplied path only to the supplied digest; nothing relates those arguments to a reviewed artifact. An accidental selection of another staged analysis workbook therefore publishes that workbook under the signed dataset's approval. The probe accepted a signed dataset with digest `bbbb…` and published caller-selected digest `cccc…`; no stored file contents were inspected by this probe. **Fix:** freeze a manifest of the final analysis and companion artifacts before signing, then validate release arguments against it. The analysis/companion split needs its own recorded digests because those files legitimately differ from the original combined workbook. Path syntax alone cannot establish the relationship.

6. **P2 — A stale registry form can append samples after processing or release.** Locations: `db/admin/migrations/0005_wave2.sql:179` and `:201`; `frontends/admin/src/app/(workspace)/sample-registry/actions.ts:26`.

   The page closes registries outside Received/Registered, and demo `recordSamples` rejects those stages. The server action checks order identity and duplicate names, while the SQL function checks only that the order is unarchived. If another operator advances the order while a grid remains open, submitting that grid still inserts new samples without reopening the workflow. The probe inserted a sample into a `processed` order and left it `processed`. **Fix:** check the allowed registry stages on the locked order inside `register_samples`, before inserting anything; return an actionable refusal from the action. This also covers direct RPC callers and avoids a race between a frontend check and the write.

The new SQL entry points themselves have pinned `search_path = pg_catalog, admin` and qualified table references. The targeted PGlite checks refused a client Requester at all six staff RPCs with `42501`; the five new internal helpers were not executable by `authenticated`. Injecting `client_id`, `order_id` and `sample_code` into `p_samples` did not override the parent-derived identity, and a foreign client's shipment was refused with `23503`. Those checks did not reveal an additional client-to-staff escape through the new RPCs.

Contract inspection found no name, argument-key or return-shape drift in the three implemented live write adapters: `receiveShipment` calls the six-argument `receive_shipment` and consumes its UUID; `registerSamples` calls `register_samples(p_order_id, p_shipment_id, p_samples)` and maps the returned sample rows, including numeric volume; `acceptResultFile` supplies all six declared `accept_result_file` arguments and consumes its UUID. There are no release-policy/sign/release adapters in `src/lib/data/` yet. The `listResultOrders` live query at `frontends/admin/src/lib/data/results.ts:40` uses existing columns and valid stage values. Parsing is behind `server-only`, and SHA-256 is calculated from the original bytes using `node:crypto` at `:50–53`; I found no browser-parser or server-crypto defect.

7. **P1 — The shipped deployment cannot support the live results upload.** Location: `frontends/admin/src/lib/data/results.ts:72`; deployment omission explicitly acknowledged at `db/admin/README.md:96`.

   Live acceptance uploads with the signed-in user's client to `admin-files` before calling the RPC. Neither the Admin migrations nor the checked-in Team storage setup provisions that bucket or its policies; `pilot/supabase/schema.sql:23` provisions only `case-files`. On a fresh deployment from these files, acceptance fails at upload; manually creating a private bucket still requires an authenticated INSERT policy. Demo acceptance skips this boundary. The staging check at `db/admin/test/staging.integration.mjs:137` supplies a path string directly to the RPC and does not exercise Storage. **Fix:** add deployment SQL for the private bucket and appropriate staff-only object policies, validating the client/order path. Keep accepted objects protected from overwrite; the current server client can continue using the user's credentials.

8. **P2 — Successful live writes lead back to an empty pipeline and a placeholder detail.** Locations: `frontends/admin/src/lib/data/orders.ts:12`, `frontends/admin/src/app/(workspace)/pipeline/page.tsx:14`, `frontends/admin/src/app/(workspace)/orders/[code]/page.tsx:10`.

   After live registration, the success banner links to the pipeline and order detail (`sample-registry/page.tsx:58`). `listOrders` always returns `[]` in live mode; the pipeline additionally bypasses the function altogether, and order detail returns a placeholder. Operators cannot see the resulting order or its progress even when the new writes succeed. The local seam probe confirmed the unconditional empty result. **Fix:** implement the authenticated order/client read mapping and connect both page branches to it. Changing only `listOrders` will leave the page-level guards in place. This is an uncompleted wave-1 integration carried into the new seam, rather than an RPC signature mismatch.

9. **P2 — The registry selects a pending shipment ahead of the shipment just received.** Location: `frontends/admin/src/lib/data/samples.ts:75`; consumed at `frontends/admin/src/app/(workspace)/sample-registry/page.tsx:111`.

   `received_at` is nullable for client-submitted shipments. Ordering descending without a null-order override puts NULL rows first. If an order already has an unreceived shipment when `receive_shipment` creates its arrival row, `liveDetail` selects the pending row, displays the wrong arrival details and passes its ID into subsequent sample registration. The probe using the query's ordering selected the seed shipment with `received_at = NULL` over a newly received shipment. **Fix:** restrict this arrival query to non-null `received_at` and order newest first, with a stable tie-breaker. If pending shipments should be shown, display/select them separately from the recorded arrival.

10. **P2 — Live dictionary additions create conflicting mappings that demo additions merge.** Location: `frontends/admin/src/lib/data/results.ts:108`; compare demo behavior at `:101` and table definition at `db/admin/migrations/0001_tables.sql:264`.

    Adding the same exact export name twice updates the existing demo entry. Live mode always inserts when the form has no ID, and the table has no uniqueness constraint for a live mapping. Two staff members, or one repeated Add submission, can persist different clean names for the same lab-wide export name. The SQL probe successfully stored both mappings. **Fix:** enforce one active mapping per export-name/scope in the database and give the live adapter a deliberate update-or-duplicate-refusal behavior; mirror that behavior in demo mode. For this lab-wide screen, a partial unique index on `export_name` where `client_id IS NULL AND archived_at IS NULL` is sufficient.

11. **P2 — The merged demo flows do not share order progress.** Locations: `frontends/admin/src/lib/data/results.ts:36` and `:82`; `frontends/admin/src/lib/data/orders.ts:13`.

    Results reads the fixed `demoOrders` and its own `le-admin-results` state, while samples and the pipeline use `le-admin-demo-store`. In a single-cookie-jar probe, receiving/registering ORD042 put it at stage 2 on the pipeline but left it absent from `listResultOrders`. Accepting the existing ORD041 returned Processed while `listOrders` still showed stage 2. Thus the separate happy paths cannot be composed into the intended workflow. **Fix:** use one per-browser order-progress source for both areas, and have both the results picker and pipeline consume it.
