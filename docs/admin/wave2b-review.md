Review of `admin/phase1..HEAD` (`48d10f4e..b1d0fcb3`), the merged Live and Release work, against the wave 2b brief and previous review. **Changes are required before live use.** The principal blockers are the dataset write bypass, publication of another client's sample columns, and the mismatch with Team's library reader.

Evidence: source inspection; a targeted PGlite probe applying this checkout's migrations and synthetic seed; and a Node probe executing this checkout's TypeScript builder, data adapters, order mapper, membership mapper and authentication function. The latter used substituted request/read/Storage adapters and real PGlite release RPCs for its lifecycle cases. Dependencies came from existing local caches: PGlite 0.3.14, TypeScript 5.9.3 and ExcelJS 4.4.0. I accept the coordinator's supplied test/build results without rerunning or independently asserting them. No part of this review accessed staging or ran the staging script. R and the real GoTrue/PostgREST/Storage services were not executed. Only this report was changed in the repository.

1. **P1 — `build_dataset` is optional: an Operator can insert an invalid build and obtain valid signatures on it.** Locations: `db/admin/migrations/0007_release.sql:30`, `:53` and `:144`; surviving grants/policies at `db/admin/migrations/0004_policies.sql:127` and `:149`; signature checks at `db/admin/migrations/0006_wave2_fixes.sql:215`.

   The new function checks the accepted source/order relationship and assigns the version, but migration 0007 leaves direct dataset INSERT enabled. The probe first received `23503` from `build_dataset` for an unrelated, merely `parsed` result file. As the same Operator, it then directly inserted a dataset for an order at Request with that source, `version = 99`, `storage_path = ''`, and arbitrary syntactically valid manifest values. Owner and Admin could each sign it, and the release RPC created a Team project. The final row was `released` while its source remained `parsed` with `order_id = NULL`. This does **not** remove the requirement for two eligible signers; it lets their approvals certify a build that never satisfied the new build contract.

   **Fix:** require the checked creation path, or enforce its source/order/path/version invariants at the table boundary. Also cover the still-granted unsigned content UPDATE path (`0006_wave2_fixes.sql:71`): revoking INSERT alone leaves `result_file_id`, `version`, paths and manifest values replaceable before signing. Arbitrary caller-supplied digests remain trusted even through the RPC; cryptographic syntax is not evidence that the builder produced the stored artifact.

2. **P2 — Withdrawal vanishes from the live order record while the page still declares “Release complete.”** Locations: `db/admin/migrations/0007_release.sql:83` and `:120`; `frontends/admin/src/lib/data/orders.ts:118`, `:125` and `:138`; `frontends/admin/src/components/order-detail.tsx:31`.

   Withdrawal archives the dataset and leaves the order at Released. The new live mapper then removes that dataset before constructing either gates or history, while deriving `released` solely from the order stage. With the only released version withdrawn, the Node probe returned `released: true`, a pending “Dataset built” gate, and history containing only “Order created.” The page consequently claims release completion and reviewer signatures, with no withdrawal reason. Superseded versions similarly disappear from history. Client users now reach this page, but cannot open the staff-only Datasets screen to discover the retirement.

   The database probe also confirmed that the client still reads the Team project, file row and Storage object after withdrawal. Retaining Team rows is an explicit brief requirement; the missing consumer-visible retirement state is the problem. **Fix:** preserve retired versions in history, display their status/reason, distinguish historical Released stage from an available current release, and provide a retirement signal for consumers of the immutable Team records. This does not require deleting Team history or silently moving the order backwards.

3. **P2 — Superseding accepts an already archived replacement.** Location: `db/admin/migrations/0007_release.sql:102`.

   The replacement query neither excludes archived datasets nor locks the replacement before checking its status. In the PGlite probe, two versions were released; an Operator archived the newer one through the permitted archive-column UPDATE; an eligible signer then successfully superseded the older version with it. Both rows ended archived, leaving no live released replacement. This is a sequential reproduction, independent of a race. An overlapping withdrawal of the unlocked replacement is an additional concurrency concern.

   **Fix:** require an unarchived released replacement and hold locks on both relevant versions through the transition, in a consistent order. Keep the same-order and increasing-version checks.

4. **P1 — A mixed-client results file publishes the other client's measurements in the target client's analysis file.** Locations: `frontends/admin/src/lib/data/release.ts:291`, `:302` and `:303`; `frontends/admin/src/lib/release.ts:87`; `frontends/admin/src/lib/release-build.ts:57`.

   The build reads only the target order's registry, but uses it solely to choose headers and metadata. An unmatched injection switches the entire export to SCIEX names; it does not prevent publication or remove the foreign column. The probe supplied two Unknown injections, ending in `ORD001-S001` and `ORD002-S001`, with only the first in the target registry. It reported one of two samples matched, then produced Abundance columns for **both** orders with values `111` and `999`. The Metadata sheet also included the unmatched second injection. Shared batches are supported by the schema and acceptance RPC, so accepting a batch-wide export for one order is a concrete trigger. The resulting file is released to that order's client viewers; database RLS cannot filter columns inside the XLSX.

   **Fix:** establish the order/client ownership of every published sample before building. Reject unresolved or foreign injections, or explicitly partition a shared batch by its authoritative injection/sample relationships while preserving values. Falling back to sample-name headers must not act as permission to publish unmatched samples.

5. **P1 — The released analysis XLSX cannot be opened through Team's current project-library flow.** Locations: `frontends/admin/src/lib/release-build.ts:13`; `frontends/admin/src/lib/data/release.ts:388` and `:391`; consumer at `R/frontends/team/project_library.R:481` and `:498`.

   The split itself is correct: the Node probe found exactly Abundance + Metadata, with every copied cell preserved and both hashes/sizes matching their generated buffers. The integration contract is incomplete. Team treats every selected `pilot_files` entry as a saved checkpoint: it downloads the object, writes a `.zip`, and calls `import_session_path`. That calls `read_session_archive`, which requires `state.json` (`R/utils_session_archive.R:66`). Inspection of the actual generated XLSX ZIP confirmed that it has no such entry. Selecting this newly released library file therefore reaches the “state.json not found in session archive” refusal, rather than opening an analysis. This conclusion is from the generated artifact and reader source, not an executed R session.

   Forwarding the two-sheet file directly to the shared Excel reader would also be insufficient: `R/utils_data.R:27` binds all sheets, so Metadata contributes extra columns/rows. Team's manual upload sheet picker is a separate path; it does not intercept library resume. **Fix:** complete an explicit dataset import boundary that sends Abundance to the matrix reader and Metadata to the metadata interface, or publish a genuinely supported library artifact. Coordinate this with the Team owner; simply changing the file extension or claiming that two sheets are Team-loadable does not solve it. The documented Nexo project-link gap does not explain this separate Team failure.

6. **P2 — Duplicate upload errors are accepted without checking the existing bytes; a signed companion can differ from its manifest.** Locations: `frontends/admin/src/lib/data/release.ts:206`, `:305` and `:383`.

   `upload` treats any “already exists”/“duplicate” message as success, assuming the path proves content identity. The sibling paths contain the full workbook's digest, not the analysis/companion's digest; even a digest-shaped path does not prevent a writer from putting different bytes there. The Node/PGlite probe returned a duplicate error for a companion path already containing 46 wrong bytes. Build completed, two genuine SQL signatures were recorded, and `releaseDataset` succeeded. The frozen manifest claimed a different companion digest and size. Only the analysis is downloaded and checked again at release. A mismatching existing analysis instead strands the new dataset when the later release check rejects it.

   **Fix:** on a recognized duplicate, read the existing object and compare its digest and size with the intended buffer; fail closed if it cannot be verified. Use each artifact's own digest or an explicit immutable artifact record for sibling paths. Verify the full/companion artifacts before accepting a build as signable. Team already follows the read-back principle in `team_library_commit` (`R/frontends/team/project_library.R:53`).

7. **P2 — Concurrent builds assign one workbook version to two different database versions.** Locations: `frontends/admin/src/lib/data/release.ts:293`, `:297`, `:303` and `:313`; `db/admin/migrations/0007_release.sql:52`.

   Each request reads the next version before generating/uploading the workbook. The RPC independently computes it later under the order lock. With both requests having read the same previous version, the Node/PGlite probe produced database versions 1 and 2, but both companion workbooks contained `dataset_version = "1"`, and both adapter calls returned `version: 1`. The SQL lock protects the unique version number; it cannot repair already-uploaded provenance. Two operators building the same order, or concurrent submissions, can therefore produce a frozen v2 whose file identifies itself as v1. The README acknowledges the two sources of truth, but consumers still receive contradictory provenance.

   **Fix:** reserve the version before constructing its artifacts, or reject a stale expected version under the database lock and rebuild before recording/signing. Reading the assigned version only after the RPC cannot correct the hashed workbook.

8. **P2 — A UTF-8 BOM changes the source digest recorded in workbook provenance.** Locations: `frontends/admin/src/lib/data/release.ts:298` and `:300`; `frontends/admin/src/lib/release-build.ts:59`; `packages/admin-ingest/src/workbook.ts:59`.

   The accepted TXT's original bytes are correctly verified, but the default `TextDecoder` removes a UTF-8 BOM. The builder then hashes the decoded/re-encoded string for `source_txt_sha256`. With the synthetic TXT prefixed by `EF BB BF`, the probe's accepted-byte digest was `a8c50e6f…521c789`, while both workbook provenance sheets recorded `783a1a88…87b8374`. The wave-1 input contract explicitly permits this BOM. The generated XLSX artifact hashes remain correct; it is the claimed source identity that is wrong.

   **Fix:** pass the verified original-byte digest into provenance, or preserve the BOM during decoding. The parser already tolerates a leading BOM (`packages/admin-ingest/src/parser.ts:5`).

9. **P3 — Failed release attempts accumulate inaccessible objects, and retries cannot recover them.** Locations: `frontends/admin/src/lib/data/release.ts:305`, `:308`, `:387` and `:389`.

   Uploads precede database finalization with no durable attempt record or cleanup. The Node/PGlite probe attempted release of an unsigned built dataset twice as an eligible signer: both real RPCs refused, while two distinct `case-files/<random-project>/<digest>` objects remained in the Storage adapter. A policy change or signature retraction after a release form was rendered produces the same sequence. The pending-upload policy allows these writes before the signature threshold is met, but there is no Team membership for the abandoned project ids, and the checked-in policies grant no deletion path to the user. The app generates another id on retry. Build upload/RPC failures can similarly strand the three Admin files. This behavior is documented, but has no implemented recovery or collection mechanism.

   **Fix:** persist a dataset-bound upload attempt/project reservation, reuse it after failures, and reconcile finalization or garbage collection through a narrowly authorized maintenance path. An eligibility/count preflight avoids known refusals but cannot replace recovery for a race or lost response. Do not add broad user DELETE/UPDATE rights to Team's bucket.

The focused storage review did **not** establish an unrestricted write or overwrite into existing Team projects. In PGlite, ordinary Operators under the default policy, client Requesters and lab Members received `42501` for pending uploads. An eligible signer could stage the recorded analysis digest before signatures; an unknown digest was denied. A pre-existing project invisible to that signer was still denied, because `is_pending_analysis_path` is SECURITY DEFINER. Duplicate INSERT returned `23505`; UPDATE changed zero rows; an upsert of a published object failed RLS. The new policy adds INSERT only, leaving Team's SELECT and mutation rules intact. It intentionally widens creation to eligible Admin signers without Team membership, for any unused UUID and any live built dataset's analysis digest; it does not bind a UUID to a specific dataset or attempt, and it does not inspect payload bytes. Finding 1 makes the “built dataset” premise weaker than the RPC checks suggest.

There is a **remaining project-creation race to validate**, rather than a reproduced existing-file overwrite: the `NOT EXISTS` at `0007_release.sql:133` neither reserves nor locks the project namespace. An upload's permission check can see a chosen UUID as unused while another transaction creates that project; the two writers share no project lock or reservation. Exploitation requires an eligible signer and knowledge/reuse of the concurrently created UUID; the app's fresh random UUIDs make accidental collision unlikely. The object unique key and lack of UPDATE permission still protect an existing object. A two-session PostgreSQL probe was unavailable because local `initdb` failed with `shmget: Operation not permitted`; PGlite's serialized session was not used to claim a concurrency proof. A reservation/finalization design should cover this interleaving.
